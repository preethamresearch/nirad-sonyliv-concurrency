The problem

Concurrency is a business number, not a vanity metric.

Peak concurrent viewers sets ad inventory, provisions CDN capacity, and justifies the price of the next rights package. It has to be defensible.

The obvious way to compute it — count a session from its first event to its last — also counts the paused player, the backgrounded app, and the client that silently went away. Nobody is watching, and the number says they are.

naive concurrency = interval overlap from session start → session end

Every figure in this deck is measured on the provided dataset: 905,558 events, 10,866 sessions, computed on ClickHouse Cloud.

The model

Two conditions, and both are required.

active = intent_playing AND client_alive

intent_playing

Toggled only by explicit transitions. VideoPlay, AppForegrounded and resume open it; pause, AppBackgrounded and VideoSessionEnd close it.

client_alive

False during total event silence beyond 120 s — three times the measured 40 s heartbeat cadence.

We tested collapsing this into one state machine. Both variants are wrong:

  • Close on a heartbeat gap → needs an explicit resume to reopen, so it undercounts a network drop mid-playback.
  • Open on heartbeats → overcounts every foreground pause, and 82% of foreground pauses keep emitting heartbeats.

Reliability

At-least-once delivery plus an idempotent sink.

Offsets commit only after the batch is durably in ClickHouse. A crash replays; the Redis dedup set turns the replay into a no-op. That is what "exactly-once" means in practice.

Replay test

fingerprint

Events are keyed by video_session_id, so every event for a session lands on the same partition. Session reconstruction is order-dependent per key — a round-robin partitioner would make ordering unrecoverable.

7 / 15
Dirty data

The judged dataset is bigger and dirtier. We tested for that.

A pipeline that has only ever seen clean input has not been tested. So we built a deterministic fault injector — 20 fault classes across schema, event, timestamp, dimension and structural categories — and ran the loader against its output.

What the original loader did

Bound columns positionally. Against a file with an extra or reordered column it does not fail — it shifts every value one column left and loads platform into country. Wrong answers that look right.

What it does now

Matches columns by name through an alias table, stages everything as String, casts in SQL where a failure is a countable zero, and aborts loudly if a required column cannot be resolved.

Result on a file with shuffled, renamed, widened and missing columns: 12 of 14 columns matched, 2 unrecognised ignored, 1 missing defaulted, 915 unparseable timestamps reported rather than silently zeroed.

A minute grid grows with total watch time. A delta model stores exactly two rows per interval regardless of duration, so it grows with the number of intervals. The gap widens as sessions lengthen — precisely what happens during the live events this metric exists to measure.

Codecs are measured, not assumed

DoubleDelta looks obviously right for 40 s heartbeats. It is wrong here: the sort key is (video_session_id, event_timestamp_ms), so rows are ordered by session, not by time — timestamps jump at every session boundary and DoubleDelta's second difference amplifies the jump. Plain Delta is 17.1% smaller, at zero read cost. Three of our four codec hypotheses were wrong; the benchmark caught them. ZSTD(6) everywhere bought 0.4% for ~20% more insert CPU — the aggressive- compression trap. Gorilla the server refuses outright: it is a float codec.

9 / 15
Correctness

Parity against an independent oracle — and a near-miss worth showing.

Intervals are verified against a separately written Python implementation. 35,902 intervals, exact parity. The gate must pass before anything ships.

The trap we fell into, and caught

Writing the obvious interval-overlap query gives 2,353 instead of 3,090 — wrong by 24%, in the flattering direction. Cause: an interval that opens and closes inside the same minute contributes +1 and −1 to that minute and cancels itself. The fix is minute containment — close at the minute after the end minute — which is why the shipped pipeline is right and the one-line version is not.

Peaks are not additive: platform peaks sum to 3,215 against a true peak of 3,090, because each platform peaks at a different minute. The dashboard states this rather than letting a reader add the column up.

13 / 15
Honesty

What we found that we would rather not have.

  • Multi-device concurrency is understated. Of 95 sessions appearing on more than one platform, 82 genuinely overlap in time — the same viewer watching on phone and TV at once. argMin attributes the session to its first platform and emits one interval, so we count one stream where there are two. 0.75% of sessions; stated rather than buried.
  • Checkpoints barely pay here. ~1.01× fewer rows read on this dataset, because 94% of events fall in a single day. The design wins at retention this dataset does not have. We report the measurement, not the theory.
  • The incremental path is slower than a full rebuild on this data, for the same reason.
  • There is no geography. Every event is country = india, with no state, city, region or CDN field. The Languages tab uses audio language as a proxy and says so on the card — 20.6% English sessions cannot be placed at all.

Three counting bugs were found and fixed during development, all the same species: summing values that do not sum — distinct sessions across groups, and peaks across dimensions.
