The model

Two conditions, both required. Collapsing them into one state machine fails in one direction or the other — and we tested both.

active = intent_playing AND client_alive

intent_playing

Toggled only by explicit transitions. VideoPlay, AppForegrounded and resume open it; pause, AppBackgrounded and VideoSessionEnd close it. Transitions are collapsed, never paired — in 65% of sessions the counts do not balance.

client_alive

False during total event silence beyond 120 s — three times the measured 40 s cadence. The data dictionary claims 60 s and is wrong; we re-measured it per platform and got 40.0 s at p90 on all ten.

Rejected approach

Close on a heartbeat gap. Needs an explicit resume to reopen, so it undercounts a network drop mid-playback.

Rejected approach

Open on heartbeats. Overcounts every foreground pause — and 82% of foreground pauses keep emitting heartbeats.

What went wrong, and what it taught us

Every item here is a bug we shipped and then caught. They are in the order we found them. Most were caught by building something adversarial rather than by reading the code again.

Silent corruption · caught by fault injection

The sealed-day loader bound CSV columns by position

The jury told us the judged dataset would be wider and dirtier. Positional binding against a file with an extra column does not fail — it shifts every value one column left and loads platform into country. Wrong answers that look right.

Worse: run_sealed.py had its own copy of the insert, so hardening the shared loader did nothing for the command that actually runs on judging day. Both paths now match columns by name through an alias table, stage everything as String, cast in SQL, and abort loudly when a required column cannot be resolved.

The verifier was the fragile part

The oracle only worked on the sample file

Our independent correctness gate hardcoded the header event_timestamp. Feed it a file where that column is renamed and it dies with a KeyError — so the loader would ingest a drifted schema correctly and the thing meant to prove it right would crash.

Then a subtler one: the loader zeroed unparseable timestamps while the oracle skipped them, so parity was comparing two different populations. Both now reject identically, matching the streaming path.

Off by 24%, in the flattering direction

The obvious concurrency query is wrong

Writing the natural interval-overlap query gives 2,353 where the truth is 3,090. An interval that opens and closes inside the same minute contributes +1 and −1 to that minute and cancels itself out. The fix is minute containment — close at the minute after the end minute.

This is the single best argument for why the model needs an independent oracle: the wrong number is plausible, and it is wrong in the direction that makes you look good.

A filter that lies

Two of four dashboard filters were silently ignored

The delta tables are keyed by platform, country, video_type and content_id. category and close_reason are not among them — so selecting a category narrowed nothing and the headline number did not move. The reader would have trusted it.

Fix: category now resolves through content_id → content_dim so it genuinely filters both curves. close_reason describes how an interval ended and is not a slice of concurrency at all, so each view now declares which filters it can honour and the UI renders only those. An ignored filter is worse than an absent one.

Three of four hypotheses wrong

We were confidently wrong about compression

DoubleDelta looks obviously right for 40-second heartbeats. It is wrong here: the sort key is (video_session_id, event_timestamp_ms), so rows are ordered by session, not time — timestamps jump at every session boundary and DoubleDelta's second difference amplifies the jump. Plain Delta is 17.1% smaller.

T64 on content_id made it 5.6% worse. user_id as LowCardinality changed nothing. ZSTD(6) everywhere bought 0.4% for ~20% more insert CPU — the aggressive-compression trap. Gorilla the server refuses outright, correctly: it is a float codec.

A design that cannot work

Our first CDC implementation captured nothing

The natural design — join the incoming row against the current table to find its predecessor — cannot work. A materialized view fires after the block is inserted, so the lookup already returns the new value. "Previous" equals "current" and every change reads as a no-op. Caught by changing a category and watching the log stay empty.

It now appends every version and diffs with a window function at read time, which is also the only formulation that stays correct when two versions land in the same block.

Measurement error, twice

We mis-measured our own throughput by 8×

The consumer reported 251 events/s. It was counting idle polling as work — the loop ran for its full time budget after the topic drained. Real throughput is 2,028 events/s. We had already extrapolated the wrong number to "7 hours for a 10× file" before catching it.

The lesson we keep re-learning: a benchmark that measures the harness instead of the system is worse than no benchmark, because it gets quoted.

Platform gotcha

Per-column compression stats are unavailable on Cloud

system.parts_columns.column_data_compressed_bytes returns 0 on SharedMergeTree. We had shipped a "footprint by column" query that would have shown a judge a table full of zeros. Totals come from system.parts.bytes_on_disk instead, and the per-column breakdown is stated as unavailable rather than faked.

What we would rather not report

These are real and unresolved. Hiding them would make everything else less believable.

Multi-device is undercounted

Of 95 sessions on more than one platform, 82 genuinely overlap in time — the same viewer on phone and TV at once. argMin attributes the session to its first platform and emits one interval, so we count one stream where there are two. 0.75% of sessions.

Checkpoints barely pay here

~1.01× fewer rows read on this dataset, because 94% of events fall in a single day. The design wins at a retention this dataset does not have. We report the measurement, not the theory.

There is no geography

Every event is country = india, with no state, city, region or CDN field. The Languages view infers region from audio language and says so on the card — 20.6% of sessions are English and cannot be placed at all.

What we would propose to SonyLIV

Findings from this dataset that point at changes worth making upstream, in the client and the event schema — not just in the warehouse.

Instrumentation

Emit an explicit playback-state field

Today pause and resume hide inside event_type='VideoHeartbeat' as a sub-field, and 82% of foreground pauses keep emitting liveness beats. Every consumer of this data must therefore reconstruct intent from a state machine, and each will do it slightly differently. A single authoritative playback_state on every heartbeat removes an entire class of disagreement between teams reporting the same metric.

Schema

Add a device instance id, distinct from the session id

82 sessions genuinely stream on two devices at once, and the schema cannot express it — so any model must either double-count or, as ours does, undercount. A device_instance_id makes concurrent multi-device viewing measurable instead of ambiguous, which matters directly for concurrency-based licensing terms.

Data quality

Fix the documented heartbeat cadence, or the tools that rely on it

The data dictionary says 60 s. The measured cadence is 40.0 s at p90 on every one of the ten platforms. Any gap threshold derived from the documented figure — including liveness alerting — is calibrated 50% too loose.

Data quality

Normalise language at the producer

hin, HIN and hin-hindi are the same language; unk, non, und and empty all mean "not stated". Worse, the first event of a session usually reports unk before the audio track resolves — so the naive read is that 80% of sessions have no language, when the real figure is 0.5%. That single artefact is the difference between "we have no language data" and "we have language data for 99.5% of sessions".

Geography

Carry a coarse region, even if only at state level

Concurrency without geography cannot answer the CDN-provisioning question it exists to serve. One low-cardinality region field would do it, and is far less sensitive than storing precise location.
